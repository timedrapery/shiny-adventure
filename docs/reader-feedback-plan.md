# Reader Feedback System: Implementation Plan

This plan records how reader feedback is added to the generated reader so
that readability problems can be found, tied to the exact passage and lexicon
decision they concern, fixed in the right layer, and re-checked with readers.
It was committed before the implementation so the design could be reviewed on
its own and so later drift from it would be visible. The implementation is
done; this document is now the record of the design decisions, and
[reader-feedback-system.md](reader-feedback-system.md) describes the system as
built.

The governed translation, the lexicon, and the newcomer evidence ledger keep
their existing authority. Feedback never edits any of them. It is evidence for
an editor to act on.

## What already exists

- The reader is generated by `scripts/generate_reader.py` from
  `docs/translations/`, the surface registry, `includes/glossary.md`, and
  `includes/newcomer-guides/`. Nothing in `reader-src/suttas/` is edited by
  hand.
- Every surface carries a translation body hash
  (`READABILITY_BODY_SHA256` in `scripts/surface_registry.py`, computed by
  `scripts/check_readability_reviews.translation_body_sha256`). Human evidence
  in `reviews/newcomer-review-ledger.json` is bound to that hash, and
  `scripts/check_newcomer_reviews.py` refuses to promote a surface to
  `validated` without the current-body evidence.
- The site is static, published to GitHub Pages, with no backend. The only
  existing feedback route is a pre-filled GitHub issue link in the
  source-and-status panel.
- The three-text pilot (AN 2.9, SN 36.6, AN 3.65) has not started: the ledger
  records zero sessions for every cohort text.
- The reader glossary already maps a reader-facing English term to a governed
  term record when the term equals a record's `preferred_translation`
  (`render_glossary` in the generator). The per-page words-used panel already
  determines which glossary terms occur on a page by exact whole-phrase
  matching, preferring the longest phrase.

## Pilot text

Enable the system on **SN 36.6, One Arrow, Not Two** first.

- It is in the Essential Five and on the stress-or-pain pathway, so real
  newcomers are likely to reach it without being recruited.
- It has the highest lexicon exposure of the three pilot texts: `felt
  experience`, `ordinary person`, `noble disciple`, `resistance`, `underlying
  tendency`, `mixed feeling`, `escape`, and four SN 36.6 phrase records. That
  is where feedback can inform lexicon decisions rather than only local
  wording.
- At about 780 words and 38 passages it is long enough to reveal
  sentence-level problems and short enough for one session.
- AN 2.9 is too short (7 passages, two governed terms) to exercise the
  grouping-by-term workflow, and its subject makes it a poor first ask of an
  anonymous public reader. AN 3.65 is the longest and most sectioned of the
  three; it is a better second text once the workflow has run once.

Draft comprehension questions are prepared for all three pilot texts. SN 36.6
was enabled first, for the reasons above; AN 2.9 and AN 3.65 followed once the
workflow had run, and `includes/feedback/config.json` now enables all three.

## Architecture

### Site side (generated, static)

- `includes/feedback/config.json`: which surfaces have feedback enabled,
  the submission endpoint, and whether optional follow-up contact is offered.
  Committed with no endpoint, so the public site shows no feedback controls
  until an operator deploys a service and sets the endpoint.
- `includes/feedback/paragraph-ids/<surface>.json`: the authoritative stable
  passage identifiers for a surface, maintained by
  `scripts/paragraph_ids.py --write` and checked by `--check` inside
  `run_checks.py`. See "Stable passage identifiers" below.
- `includes/feedback/term-maps/<surface>.json`: explicit, editor-written
  mappings from a passage identifier to governed term ids. Optional per
  surface.
- `includes/feedback/comprehension/<surface>.json`: versioned comprehension
  question sets with `editorial_status` of `draft` or `approved` and
  assessment guidance. Questions are shown only for enabled surfaces.
- The generator embeds, on each enabled page, a JSON manifest carrying the
  surface key, body hash, ordered passage ids with text fingerprints, term
  mappings with their basis, glossary explanation versions, the introduction
  version, and the comprehension question set with its version. It also emits
  the optional comprehension review form and a short note on how feedback is
  used. Nothing in the governed translation body is changed.
- `reader-src/javascripts/reader-feedback.js` adds, only when the endpoint
  answers a health probe, a discreet "Give feedback" button after each
  passage, "Did this explanation help?" controls in the words-used panel and
  guide key words, one button on the "Before you read" section, and wires the
  comprehension form. Everything is keyboard-operable, uses native form
  controls with labels, moves focus predictably, and announces success and
  failure with live regions. A failed submission keeps the form contents and
  can be retried with the same client submission id.
- `scripts/build_book.py` strips feedback furniture from the EPUB.

### Service side (separately deployable)

`feedback_service/`, a small WSGI application using only the Python standard
library and SQLite. Rationale: the repository is already Python-first with a
deliberately short dependency list; SQLite needs no external account; a WSGI
app runs locally with `wsgiref` and in production under any WSGI server
(gunicorn, waitress) or a container, without code changes.

- `POST /api/submissions`: public. Validates target, category, lengths, the
  version fields, and a client-generated submission id. The same id submitted
  twice returns the first result without a second row. Payloads over a fixed
  byte limit are rejected. A honeypot field and a per-client sliding-window
  rate limit provide proportionate spam protection. Origins are checked
  against a configured allowlist for CORS.
- `GET /api/health`: public probe used by the reader.
- `/admin/...`: maintainer-only, HTTP Basic authentication over HTTPS against
  a PBKDF2 password hash supplied by environment variable. No default
  credentials; the admin routes refuse all requests until configured. Pages
  are server-rendered with every stored string escaped, sent with a
  Content-Security-Policy that forbids scripts. Form posts carry an HMAC
  token.
  - queue with filters by surface, passage, term, category, version, status,
    channel, and target
  - a detail view where the maintainer records the lifecycle step, the
    observed problem, where the fix belongs (translation, glossary,
    introduction, shared lexicon), the rationale, the change reference, and
    follow-up evidence; every change is appended to a history table
  - a by-term view grouping submissions across surfaces
  - session management for formal review sessions and per-participant
    assessment of comprehension responses
  - JSON export of the queue and a reviewed export of one formal session
- Storage: SQLite with numbered SQL migrations applied by the service on
  start-up and by `python -m feedback_service migrate`. The optional
  follow-up contact, when enabled, lives in a separate table with the consent
  text recorded, and is deleted independently.
- Operations: `backup`, `purge --older-than`, `delete --id`, and
  `hash-password` commands. Request logs record method, path, status, and
  submission id only.

### Evidence path back into the repository

`scripts/stage_feedback_evidence.py` takes a reviewed session export, checks
each record against the current body hash and the ledger's field contract,
and, with `--write`, appends the records to the surface's `newcomer_reviews`.
It refuses public-channel records, unassessed records, and records for a body
other than the one the participant read. `scripts/check_newcomer_reviews.py`
remains the gate, unchanged.

## Stable passage identifiers

A passage is a blank-line-separated block inside the `## Translation` section
that is not a heading. Identifiers are `p` followed by a zero-padded sequence
number allocated per surface (`p001`, `p002`, ...) and are never reused.

`scripts/paragraph_ids.py --write` aligns the current body with the recorded
map:

- an unchanged passage (same normalized text) keeps its id, wherever it moved;
- an edited passage that sits between the same neighbours keeps its id, and
  its fingerprint is updated; the old fingerprint is kept in the map's
  history so feedback recorded against it is still identifiable;
- a split: the first part keeps the id, later parts get new ids with
  `split_from`; a merge: the surviving block keeps the first id and the
  others are retired with `merged_into`;
- a new passage gets a new id; a removed passage is retired with
  `retired_in` set to the body hash that removed it.

Feedback records carry the passage id, the exact wording shown, and the body
hash, so a record can always be read against the text the reader saw even
after any of the above.

## Term mappings

Feedback carries term ids only from two explicit sources:

1. the editor-written per-surface term map, marked `explicit`;
2. the page's existing words-used panel, where a glossary term occurs in the
   passage as a whole phrase and that glossary term equals a governed
   record's preferred rendering, marked `glossary`.

Anything else is `unmapped`. The queue shows the basis with every term, and
the maintainer can confirm or correct the mapping in the disposition. The
bounded mapping work for the pilot is the explicit map for SN 36.6.

## Formal sessions and counting

- Public submissions carry `channel = public`. They never appear in a session
  export and cannot count toward the newcomer threshold.
- A facilitator creates a session in the admin area and lists anonymous
  participant labels, marking each as `fresh` or `returning` (with the earlier
  participant it continues). Participants open the page with a session link;
  their submissions carry `channel = formal`, the session, and the label.
- Within one session and one body version, a participant's second
  comprehension response is stored but marked superseded and does not count.
  The same label in a later session against a new body counts again, as a
  returning reader, and the export says so.
- The reviewed export includes only assessed formal comprehension responses
  and maps them onto the ledger's fields. The ledger checker still requires a
  human to run it.

## Sequence of work

All nine steps are done.

1. Commit this plan.
2. Passage identifiers: script, maps for the three pilot texts, tests,
   `run_checks.py` entry.
3. Feedback inputs: config, term map and comprehension drafts, loader and
   validator, tests.
4. Generator and reader: manifest, review form, About note, JavaScript, CSS,
   build_book stripping, regenerated pages, source-level checks.
5. Service: migrations, validation, submissions, admin queue, sessions,
   export, operations commands, tests.
6. Evidence staging script and tests.
7. Browser tests for the reader behaviour against the running service.
8. Documentation: system guide, operator procedures, facilitator guide,
   changelog, script index, roadmap cross-links.
9. Full verification suite, strict site build, rendered checks.

## Out of scope for the first version

- Text-selection feedback (the passage-level control is sufficient and does
  not require a selection).
- Feedback on the standalone glossary page (the per-page panel is covered).
- Any automatic revision of translations, glossary text, lexicon policy, or
  readability status.
- Any AI-assisted triage. If added later it must remain advisory, must never
  hide the original response, and must never take a lifecycle step by itself.
