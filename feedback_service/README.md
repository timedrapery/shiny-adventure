# Reader feedback service

The submission service behind the reader's "Give feedback" controls. The
reader site is static (MkDocs on GitHub Pages), so this small service is
deployed separately and the page talks to it across origins.

Stack: Python 3.11+, standard library only, SQLite. The application is a
plain WSGI callable, so it runs locally with `wsgiref` and in production
under any WSGI server or container. There are no accounts to create and no
paid dependencies to try it locally.

## Run it locally

From the repository root, with the reader already built (`mkdocs build`):

```bash
python -m feedback_service hash-password           # prints a hash; paste it below
export FEEDBACK_MAINTAINER_USER=editor
export FEEDBACK_MAINTAINER_PASSWORD_HASH='pbkdf2_sha256$...'
export FEEDBACK_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')"
python -m feedback_service serve --site-dir site
```

Then open `http://127.0.0.1:8765/suttas/sn36-6-salla-sutta/`. Because the
service serves the built site itself, the page's health probe succeeds on the
same origin and the feedback controls appear. The maintainer queue is at
`http://127.0.0.1:8765/admin/`.

Data lives in `feedback-data/feedback.sqlite` (git-ignored) unless
`FEEDBACK_DB` says otherwise.

## Configuration

| Variable | Meaning | Default |
| --- | --- | --- |
| `FEEDBACK_DB` | SQLite file | `feedback-data/feedback.sqlite` |
| `FEEDBACK_SITE_DIR` | serve a built reader from this directory (local trials only) | unset |
| `FEEDBACK_ALLOWED_ORIGINS` | comma-separated origins allowed to call the API cross-origin | none |
| `FEEDBACK_MAINTAINER_USER` | maintainer login | unset: admin disabled |
| `FEEDBACK_MAINTAINER_PASSWORD_HASH` | from `hash-password` | unset: admin disabled |
| `FEEDBACK_SECRET_KEY` | HMAC key for form tokens and client pseudonyms | ephemeral per run |
| `FEEDBACK_MAX_BODY_BYTES` | request size limit | 32768 |
| `FEEDBACK_RATE_LIMIT_PER_HOUR` | submissions per client per hour | 30 |
| `FEEDBACK_TRUST_PROXY` | `1` to read `X-Forwarded-For` behind a reverse proxy | off |
| `FEEDBACK_ALLOW_CONTACT` | `1` to accept an optional consented email for follow-up | off |
| `FEEDBACK_RETENTION_DAYS` | documented retention, applied by the `purge` command | unset |

## Endpoints

- `GET /api/health`: probe. The reader shows feedback controls only when this
  answers.
- `POST /api/submissions`: JSON body. Validated field by field; over-size
  bodies get 413, bad shapes 422. The `client_submission_id` is unique: a
  retry returns the original id with `duplicate: true` and stores nothing.
  A filled honeypot field is answered with 200 and discarded. Each hashed
  client gets `FEEDBACK_RATE_LIMIT_PER_HOUR` submissions per hour.
- `/admin/...`: HTTP Basic authentication. Queue, by-term view, sessions,
  exports. No scripts are served; every stored string is HTML-escaped; forms
  carry an HMAC token and cross-site posts are refused.

What a submission carries is decided by the page manifest generated by
`scripts/generate_reader.py`: surface key and label, translation body hash,
passage id, fingerprint, and exact wording shown, governed term ids with
their mapping basis, glossary explanation versions, introduction version,
and, for comprehension reviews, the question set version, hash, and
editorial status. The service records the receipt time.

## The maintainer queue

- **Queue** (`/admin/`): filter by sutta, passage, term, category, version
  (body hash prefix), status, channel, target, or session. Export the
  filtered view as JSON.
- **Submission detail**: what the reader saw, the original response, the
  governed terms (with `explicit` or `glossary` basis, or "unmapped"), and
  the editorial record. Record a disposition: lifecycle step (received,
  examined, proposed change, revised, checked with readers), the observed
  problem, where the fix belongs (translation, glossary, introduction, shared
  lexicon, or no change), the rationale, a reference to the change, and
  follow-up evidence if actually collected. Every disposition is appended to
  the history; nothing is overwritten.
- **By term** (`/admin/terms`): submissions grouped by governed term across
  texts, so repeated confusion about one rendering can be seen as a lexicon
  question.
- **Sessions** (`/admin/sessions`): formal review sessions with anonymous
  participant labels. A participant link is
  `<reader page>?session=<code>&participant=<label>`. Responses through a
  link are `formal`; everything else is `public` and can never count.

The queue never edits a translation, a glossary entry, a term record, or a
readability status. The disposition points at the change made in the
repository.

## Formal sessions and the evidence ledger

1. Create a session for the text and add participant labels, marking
   returning readers with the earlier session and label.
2. Participants read the page through their link and complete the optional
   review. One comprehension response per participant per body version
   counts; later ones are kept but marked as not counting.
3. Assess each response against the question set's guidance (`pass`,
   `fail`, `unclear`) and record whether the session was independent.
4. Export: `python -m feedback_service export-session --code CODE --out session.json`
   (or the JSON link on the session page). Only assessed, counted responses
   with recorded independence are included; the rest are listed as excluded
   with the reason.
5. In the repository: `python scripts/stage_feedback_evidence.py --export session.json`
   shows what would be added to `reviews/newcomer-review-ledger.json` and
   whether it counts against the current body; `--write` appends it after
   the ledger check passes.

## Data handling

Stored by default: the feedback text, the passage and page it concerns, the
version fields above, a receipt time, the lifecycle record, and, for formal
sessions, the anonymous participant label. Not stored: names, accounts,
addresses, user agents. Client addresses are hashed with a daily key for
rate limiting only and are never written alongside a submission.

Optional contact (`FEEDBACK_ALLOW_CONTACT=1`): an email address is accepted
only with explicit consent, stored in a separate table with the consent
text, excluded from every queue view and export, and deletable on its own.

Logs record method, path, status, and public submission id. Bodies are not
logged.

### Backup

```bash
python -m feedback_service backup --out /path/to/backups/
```

Writes a consistent copy via SQLite's online backup API. Back up before a
purge and before deploying a migration. Keep backups under the same access
controls as the live database; they contain reader text.

### Retention and deletion

Set `FEEDBACK_RETENTION_DAYS` to the published retention period and run the
purge on a schedule:

```bash
python -m feedback_service purge --older-than "$FEEDBACK_RETENTION_DAYS" --dry-run
python -m feedback_service purge --older-than "$FEEDBACK_RETENTION_DAYS"
```

Delete one submission (and its terms, dispositions, and contact) or only
its contact record:

```bash
python -m feedback_service delete --id fb_xxx
python -m feedback_service delete --id fb_xxx --contact-only
```

Evidence already staged into the repository ledger is governed by the
ledger, not by the service; purging the service does not remove it.

### Migrations

`migrations/NNN_name.sql` files are applied in order and recorded in
`schema_migrations`. The service applies pending ones on start;
`python -m feedback_service migrate` applies them without serving. Add a
new numbered file for a schema change; never edit an applied one.

## Deploying

The public site does not show feedback controls until
`includes/feedback/config.json` carries the service's origin as `endpoint`
and the reader is regenerated. Steps:

1. Choose a host that runs a Python WSGI app with a persistent disk (a small
   VM, a container platform with a volume, or a PaaS with persistent
   storage). SQLite needs one writable instance; do not run replicas
   against one file.
2. Run under a production WSGI server (for example
   `gunicorn 'feedback_service:create_app()'`) behind HTTPS. Set
   `FEEDBACK_TRUST_PROXY=1` only when a reverse proxy sets
   `X-Forwarded-For`.
3. Set `FEEDBACK_ALLOWED_ORIGINS=https://timedrapery.github.io`,
   the maintainer variables, `FEEDBACK_SECRET_KEY`, `FEEDBACK_DB` on the
   persistent disk, and `FEEDBACK_RETENTION_DAYS`.
4. Schedule `backup` and `purge`.
5. Set `endpoint` in `includes/feedback/config.json` to the service origin,
   run `python scripts/generate_reader.py --write`, commit, and let the
   deploy workflow publish the reader.
6. Open the pilot page and confirm the controls appear and a test
   submission reaches the queue; then delete the test submission.

Until step 5 is done the public site is unchanged.
